## Step 4 -- does `-g` explain it, and is a line-number shift the mechanism?

build_flags_check.txt: every one of `_strata`'s 19 compile commands (a standalone SKIP_TESTS=1
build at 565fab2, used only to read compiler flags) carries `-g` (from CPython 3.12's sysconfig
CFLAGS on Ubuntu: `-fno-strict-overflow -Wsign-compare -DNDEBUG -g -O2 -Wall -fPIC ...`, with this
project's own `-std=c++20 -O3 ... -march=native` appended after -- `-O3` wins over the base `-O2`,
`-g` stays on). So every object carries DWARF debug info, including per-instruction source
file/line (DILocation), derived from the *raw* source file's line numbers -- not from the
preprocessed/token-normalised stream that `token_identity.sh` compares.

source_diff_shape.txt: base..head touches exactly the three named files, and every hunk in two of
them is a preprocessor guard around code `_strata` already had:
  - python_dumps.cpp: +535/-26 lines, 7 new `#if defined(STRATA_DUMPS_HOOK)` blocks (dead code for
    `_strata`, where that macro is undefined -- doesn't compile in, so no new tokens for `_strata`,
    but the `#if`/`#endif`/comment lines still occupy line numbers in the file).
  - python_files.cpp: +7/-0, python_folder.cpp: +17/-2, both wrapping their *existing* function
    bodies in `#if !defined(STRATA_DUMPS_HOOK)` ... `#endif` (true for `_strata`, so the code is
    included unchanged -- same tokens, but preceded by new guard/comment lines that shift every
    line number below them in the file).

This is consistent with the M15b design record's own claim (identity-m1 evidence, docs/decisions.md
2026-09-29 "Flag shape (M15b)"): `_strata`'s 18 TUs are *token*-identical to base on both ISAs
(`token_identity.sh`, which compares preprocessed token streams). Token identity does not imply
line-number identity: the guard directives this diff adds shift the raw source's line numbers for
every following line in the same file, so a compiler that emits `-g` records different DILocation
line attributes for the *same* instructions. LLVM's ThinLTO per-module hash (the source of the
`.llvm.<N>` promoted-local-name suffix, docs/decisions.md 2026-09-27) is computed over the module's
IR, and debug metadata is part of that IR -- so a line-number-only source change, with zero token
or instruction change, is sufficient to move the hash, reorder ThinLTO's promotion/link, and shift
GOT-slot placement, without changing a single instruction. Nothing else changed here: same
compiler, same flags, same build directory, same profile bytes (step 2 pins all three), and step
3 finds zero instructions differing beyond page-offset immediates. This is not proven by direct
DILocation inspection (no such probe was run this session); it is the mechanism consistent with
every artifact gathered (-g on, guard-only diff in exactly the touched files, code-identical
disassembly, build-noise ruled out) and with the class of cause the 2026-09-27 precedent already
established for this same leg (module hash following something other than instruction content).

## Answer: code or layout?

**Layout, not code.** Every one of `_strata`'s compiled instructions is unchanged between base
38eaa9f and head 565fab2 on linux-arm64 (0 functions differ beyond ThinLTO suffix/address
normalisation and GOT-slot immediates, in both the direct and noise-controlled pairs). The failing
held-profile identity gate is driven by a link-order change downstream of a ThinLTO module-hash
shift, most likely triggered by `-g`-recorded line-number movement from preprocessor guards added
around otherwise-unchanged code in python_files.cpp/python_folder.cpp and dead-for-`_strata` guards
added in python_dumps.cpp -- not by any behavioural or codegen change. Build/profile nondeterminism
is ruled out directly (step 2's A vs A_held is byte-identical, build-id included).
